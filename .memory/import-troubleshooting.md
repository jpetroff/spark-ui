# Import diagnostics and recovery

This runbook describes the current code in `scripts/vendor/{command,import,graph,aliases,ledger,update,merge}.ts` and the Makefile wrappers. See [Ark/Zag source importer](registry-source-importer.md) for the source layout and registry architecture. Commands below run from `spark-ui/`. Replace `REVIEW_BRANCH`, `SOURCE_BRANCH`, `CANDIDATE_BRANCH`, and example commit values with actual names from the ledger; they are placeholders, not shell variables.

## 1. Capture the state before retrying

Start with read-only inspection. A failed command may have already created branches, advanced the baseline, written sources, or completed the target merge.

```sh
git status --short
git branch --show-current
git log --graph --decorate --oneline -20
git branch --list 'vendor/*' 'update/*'
git worktree list --porcelain
git diff --name-only --diff-filter=U
git diff --stat
git diff --cached --stat
git rev-parse --verify refs/heads/vendor/upstream
```

The last command fails normally before bootstrap. An empty current branch name indicates detached HEAD. Unmerged files identify an unresolved merge, but also inspect full `git status`: a resolved merge may still need its merge commit.

Read the ledger's compact operation list and then the relevant full record:

```sh
node --input-type=module -e 'import fs from "node:fs"; const l = JSON.parse(fs.readFileSync(".import.lock.json", "utf8")); console.table(l.operations.map(o => ({id: o.id, mode: o.mode, phase: o.phase, status: o.status, requested: o.requestedComponents.join(", "), review: o.branches.review?.name, target: o.merge?.target})))'
node --input-type=module -e 'import fs from "node:fs"; const l = JSON.parse(fs.readFileSync(".import.lock.json", "utf8")); console.log(JSON.stringify(l.operations.at(-1), null, 2))'
```

The second command shows the latest record, which need not be the operation you intend to recover. Inspect its ID and branch names first. These snippets parse JSON for inspection; the importer performs stricter schema validation. Do not delete the ledger to bypass a diagnostic, force-delete service branches, or reset the baseline before preserving and understanding the recorded work.

Source locations are `ARK_SOURCE` / `ZAG_SOURCE`, defaulting to `../ark` / `../zag` relative to the Spark repository root. They must point to usable Git worktrees with the selected committed objects. The scripts do not read `ARK_DIR` / `ZAG_DIR` as source-selection inputs.

| Operation                                   | Ark/Zag revision precedence, independently for each source                                                                                        |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| First direct import with no source manifest | That source's committed `HEAD`.                                                                                                                   |
| Later direct import or import dry run       | Commit in `vendor.lock.json`; fall back to `HEAD` only when no previous manifest exists. Exported `ARK_REF` / `ZAG_REF` are ignored on this path. |
| Applying public import after bootstrap      | Nonempty exported `ARK_REF` / `ZAG_REF`, otherwise the corresponding locked commit.                                                               |
| `make update` / `make update-upstream`      | Supplied Make ref value or `HEAD` for each omitted/empty ref. The wrapper sets both environment variables.                                        |
| Direct `update.ts` invocation               | Nonempty `ARK_REF` / `ZAG_REF`, otherwise the corresponding locked commit.                                                                        |

Snapshot construction rejects any tracked changes in either upstream worktree, even when importing a different committed ref. Untracked upstream files are ignored and never imported. The importer reads Git objects and never fetches, installs upstream dependencies, commits upstream changes, or switches upstream branches. A component visible only in upstream working-tree changes is unavailable to the importer.

## 3. Generation checks and write boundaries

The generator builds the union of locked components and requested names, deduplicates it, and sorts it. The lock is read from the checkout where generation runs: in the isolated workflow this is the candidate based on `vendor/upstream`. Because that baseline advances before final target merging, it can already include components from another pending review. Starting a new import from an older source branch can therefore bring those earlier baseline components into the new review too. Branch labels count unique requests, not the complete generated set; inspect `components`, the report, and Git diff. Importing fewer names does not remove older public components. Removing a component is not a supported import-command operation.

Checks occur before source writes:

1. Read and parse an existing `vendor.lock.json`; validate names with `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`. Uppercase names, underscores, slashes, and whitespace are invalid.
2. Validate clean tracked upstream worktrees, resolve selected refs as commits, and enumerate their committed files. Direct generation cannot advance previously locked revisions; isolated baseline generation can.
3. Discover `@ark-ui/*` / `@zag-js/*` package manifests and visit React/Svelte component or provider `index.ts` entry points. Emit a warning for each unavailable framework implementation. A requested component with neither framework fails the entire batch. This explicit no-implementation error checks requested names; inspect warnings for previously locked components too.
4. Traverse the complete runtime/type dependency closure. Resolve relative modules, Svelte `$lib/`, package source exports and supported conditions/wildcards. Preserve canonical shared/context identities and reject excluded tests, stories, and examples.
5. Check Ark-to-Zag dependency edges against Ark's declared Zag version requirements. Require external packages to have declared dependency/peer ranges, reject local workspace/file/link external ranges, and intersect external ranges within each public entry's closure. This does not prove full runtime or consumer dependency compatibility.
6. Read both committed upstream license files. Construct generated source output, starter paths, and the source manifest. Required package manifests such as `@ark-ui/react` and `@zag-js/core` must exist; malformed or missing metadata may surface as JSON/type errors rather than a dedicated importer error.
7. Check ownership. Direct generation refuses a still-required locked source deleted locally, or a modified locked source whose content differs from both its recorded generated hash and proposed new output. Both modes refuse to replace a differing unowned generated-source destination, except license output. Existing starter entrypoints/CSS are seeded only if absent and are not overwritten by this collision rule.
8. Prepare missing package TypeScript configs and format them. Existing configs are preserved without migration or correctness checks. Print/save the generation report before applying files.

When applying, the write order is generated sources/licenses, deletion of obsolete locked sources, missing starters, missing package configs, root alias synchronization and formatting, then `vendor.lock.json`. Application is not a filesystem transaction. A permission error, full disk, bad root config, or formatter failure can leave partial files and the previous manifest. A saved report proves planning finished; it does not prove writes completed.

`report.changed` covers generated output and missing package configs. It does not enumerate every starter or root-alias change. `report.files` counts generated output, not every file that Git may commit. Compare the Git diff as well as the report.

New package configs extend `../../tsconfig.json` and include `src`, including internal dependency/shared source roots. They are not consumer registry files. The root `ES2023.Array` library declaration supplies Date Picker's `findLastIndex` types. These editor configs do not replace the framework-aware React/Svelte checks.

## 4. Bootstrap and isolated update phases

Bootstrap has no new ledger record. It requires a clean checkout, an attached branch other than `vendor/upstream`, an existing readable source manifest, matching hashes for all locked generated implementation files, and a committed `HEAD`. It creates `vendor/upstream` without switching to it. A missing locked file fails on read; an existing baseline branch fails normal Git branch creation. Starter/CSS customization is not part of the generated-file hash loop.

Treat `vendor/upstream` as importer-owned generated history. Baseline regeneration deliberately skips the direct-generation modified/deleted-file guards for locked sources; committing customizations to that permanent baseline does not protect them from regeneration. Bootstrap is selected whenever `--bootstrap` is present and does not validate its other arguments; invoke it on its own.

Ordinary updates and bootstrapped imports start a ledger record before most preflight checks. They require a clean Spark checkout, including untracked nonignored files, a committed starting branch other than `vendor/upstream`, and a local baseline ref. Without `--bootstrap`, any update flag is rejected. An edited Makefile, an edited documentation file, or another untracked file is enough to trigger `Branch operations require a clean checkout` until committed or stashed. A new local ledger record can still have been written despite the message's “nothing was changed” wording.

| `phase`       | Operation and possible residual state on failure                                                                                                                                                                                                                                                                                 |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `validation`  | Read ledger/Git state, source manifest, selected source refs, and branch label. No candidate creation yet. Invalid source refs leave the permanent baseline and original branch unchanged. Failures before `startOperation` finishes may have no record.                                                                         |
| `candidate`   | Record the planned candidate name/base commit, then switch to a new candidate based on `vendor/upstream`. A recorded name is intent, not proof that branch creation succeeded.                                                                                                                                                   |
| `generation`  | Generate all components with baseline ownership rules; stage `packages`, `vendor.lock.json`, `tsconfig.json`; commit if staged changes exist. Failures may leave a dirty candidate, staged files, or a new commit. No automatic rollback/switch-back occurs.                                                                     |
| `baseline`    | Record candidate tip, then move `vendor/upstream` to it. If movement fails, candidate remains. Check actual refs; the phase is saved before the command.                                                                                                                                                                         |
| `integration` | Record a planned review ref, create it from the original source branch, and merge `vendor/upstream` normally. At this point the baseline has already advanced. A Git failure is reported as `conflicted`; inspect Git output/status to distinguish true source conflicts from hooks, permissions, locks, or another Git failure. |
| `registry`    | Record merged review tip, run `import.ts registry`, stage/commit `registry.json` if changed. Registry or commit failure leaves the review branch and advanced baseline available for recovery. Generated ignored artifacts can already exist.                                                                                    |
| `review`      | Set `ready` after registry metadata/commit succeeds. Remain on the review branch for inspection and validation. The original source branch ref has not moved.                                                                                                                                                                    |

Git commands use the configured identity, falling back per missing setting to `Spark UI Importer <spark-ui-importer@localhost>` through command-local `-c` arguments. Hooks, signing policies, repository permissions, preexisting Git locks, branch collisions, and a baseline checked out in another worktree can still prevent switches, commits, or baseline advancement. There is no fetch, push, pull request, or automatic remote cleanup.

### Recover generation or integration

- For generation/staging/commit failure, preserve the dirty/staged candidate and inspect the last events and actual diff. Correct the underlying issue before choosing to finish or discard that candidate. Starting another public import while still on a candidate is not a resume operation; it starts another ledger record. Return to the intended normal source branch only after preserving the candidate work.
- For an integration conflict, resolve on the review branch, stage resolved paths, and create the merge commit. Then run `pnpm registry:build`, inspect/commit changed `registry.json`, and run validation before switching to the intended target and using `vendor:merge REVIEW_BRANCH`. The ledger may still say `conflicted`/`failed`; merge eligibility checks ancestry rather than requiring `ready`.
- `git merge --abort` aborts the current Git merge only. It does not restore the previous `vendor/upstream` tip, remove candidate/review refs, or clear the ledger. An aborted review usually lacks the candidate commit and will fail the final merger's ancestry guard. Finish the integration deliberately or preserve it for investigation; repeatedly starting imports is not rollback.
- On registry-phase failure, finish registry generation and commit metadata on the existing review branch. Review any artifact/config changes and validate before final merge. The merge helper does not repair or verify registry metadata automatically.

## 5. Ledger semantics and logging limits

`vendor.lock.json` is committed source provenance. `.import.lock.json` is Git-ignored local history, excluded from formatting, and retained across checkout changes. It is not shared by cloning/pushing review branches, nor automatically shared between separate worktrees. It is not an interprocess mutex; run one importer/merger at a time in a checkout. Branches created before ledger support have no automatic discovery/migration.

Schema version is `1`. Reads validate the operations array, unique nonempty IDs, recognized mode/status, required source/events/branch shapes, hexadecimal commit fields, candidate/review branch prefixes, and optional upstream/report/merge/cleanup shapes. Only `candidate` and `review` branch roles are accepted. This is shape validation, not proof of Git ancestry or branch existence; the merge helper performs those checks separately. Source manifest version/importer version are distinct fields in `vendor.lock.json`.

| Field                               | Meaning and caveat                                                                                                                                                                                                                                      |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `requestedComponents`, `components` | Unique sorted user requests versus the resulting public component set. Internal dependency roots appear through reports/source mappings, not necessarily as public components. Early failure can leave `components` empty or only planned.              |
| `source`                            | Starting branch and commit; commit may be `null` before the initial Spark commit for direct imports. Applying imports require an attached branch; a detached start can fail before an operation is saved.                                               |
| `upstream`, `report`                | Resolved source commits, later enriched with versions/report data. Fields can be absent before resolution; reports are saved before filesystem application.                                                                                             |
| `branches`                          | Planned/recorded candidate and review names and commits. Candidate commit is updated after generation; review commit is updated after integration/registry. Failed or killed commands can leave planned names or earlier tips. Inspect actual refs too. |
| `phase`, `status`                   | Last saved checkpoint/outcome, not a transactional guarantee. `running` can remain after a kill. `failed`/`conflicted` does not mean all previous steps were undone.                                                                                    |
| `events`                            | Timestamp, `info`/`warning`/`error`, and message. Captured command invocation and output plus generation warnings and caught errors. Successful command stdout is info; stderr is warning even for normal Git progress. Failed stdout/stderr are error. |
| `merge`                             | Chosen target branch, review tip selected for the target merge, and successful/resulting target commit when recorded. Retries are bound to that target.                                                                                                 |
| `cleanup`                           | Latest attempt's per-branch `deleted`, `missing`, or `retained`, with reasons. The array is rebuilt for each retry; event history preserves earlier attempts.                                                                                           |

Statuses: `running` = active/interrupted step; `imported` = direct generation applied; `ready` = review generation/metadata succeeded; `failed` = caught non-conflict failure; `conflicted` = integration/target Git merge failed; `merged` = target merge recorded but cleanup unfinished; `complete` = cleanup finished. Direct `imported` records have no review branch to merge.

Each save validates the existing ledger, writes `.import.lock.json.<uuid>.tmp` exclusively, and renames it over the root ledger. This prevents readers seeing half-written JSON; it does not make Git/source writes atomic or guarantee a record survives every process/filesystem failure. Do not edit the ledger while commands run. A failed save can prevent subsequent diagnostic saves; an orphan temporary file may remain after a kill.

Public import argument errors, Make parsing errors, bootstrap failures, malformed ledger reads, and failures before record creation can be terminal-only. Merge selection/preflight refusals generally do not add an event. Standalone registry/verification and manually run validation commands do not append their output to import history. Empty events or unchanged status do not prove a command was never attempted.

If a ledger is missing, imports can start a new history, but `vendor:merge` refuses to operate on unrecorded review branches. If malformed, restore a trusted local backup and validate it against actual Git refs. One invalid record blocks the whole file; do not invent SHAs or erase unrelated history to force selection. Recovery without a trustworthy ledger requires deliberate manual Git inspection/merging/cleanup outside the automatic script.

An older baseline checkout may predate the `.gitignore` entry, making the local ledger appear untracked while inspecting a candidate. Preserve the ledger and check the actual ignore rules rather than adding it to the source baseline commit.

## 6. Target merge checks and recovery

`vendor:merge` reads the ledger before selecting a record. Explicit names must match a recorded **review** branch exactly. With no name, every record with a review reference and status other than `complete` participates, including failed/interrupted records whose planned branch was never created. More than one match requires an explicit review name. Unrelated branches and direct-import records are not selected.

After selection, checks run in this order:

1. Require clean Spark `git status --porcelain`, including untracked nonignored files, and an attached target branch.
2. Reject `vendor/upstream`, all `vendor/candidate-*`, and all `update/upstream-*` targets. Switch from the review branch to a normal intended destination before invoking the command. The target need not be the original import branch.
3. If a previous target merge was recorded, require the same `merge.target` on retry, even after aborting its Git merge. Explicitly selecting an already `complete` operation on its target returns an already-complete message after checkout/target checks; it does not recreate deleted branches.
4. Require a candidate baseline in the record. Before the first successful target-merge record, require a local review ref whose tip contains both the recorded review commit and candidate commit. Candidate branch existence is not required if the recorded candidate commit remains reachable in the review.
5. If an unfinished target merge already recorded `merge.sourceCommit`, require the review tip to remain equal to it. Do not amend/rebase/advance that review while resolving the target merge. Before the first target attempt, ordinary descendant review commits are allowed.
6. Save the selected target/review tip and merge normally, unless that exact review tip is already an ancestor of the current target. On failure, record `conflicted`, preserve Git merge state and all service branches, and exit nonzero.
7. Save the resulting target commit and `merged`. On cleanup-only retries with an existing successful merge record, require both recorded merge commit and review source commit to remain ancestors of current `HEAD`; refuse cleanup after a history rewrite that loses them.

| Message or state                                              | Resolution                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Missing .import.lock.json` / `Malformed .import.lock.json`   | Restore trustworthy local operation metadata; pushing a review branch does not transfer this file. No automatic selection/deletion occurs.                                                                                                                                                           |
| `No matching pending import review branch`                    | Check explicit spelling, ledger review names, and whether only direct imports/completed operations exist. Candidate names are not accepted. Old/unrecorded branches require manual investigation.                                                                                                    |
| `Several imports are pending`                                 | Select one review explicitly; do not assume the newest record is the desired one. Failed planned review refs also count.                                                                                                                                                                             |
| Clean-checkout or detached-HEAD refusal                       | Commit/stash intended changes, finish/abort any merge deliberately, and switch to a normal target. Stashing during a conflict is not a replacement for resolving/aborting it.                                                                                                                        |
| `service branches cannot be merge targets`                    | Switch to the branch that should receive the import, such as `main` or a development/release branch.                                                                                                                                                                                                 |
| `This merge was started on ...`                               | Return to the recorded target to finish or retry that operation. The helper does not migrate an existing merge attempt to another target.                                                                                                                                                            |
| `Import record has no candidate baseline`                     | The record is incomplete/inconsistent; inspect source history and restore correct metadata before relying on automation.                                                                                                                                                                             |
| `Missing local review branch`                                 | A remote ref alone is insufficient. Restore the reviewed local ref from verified history; do not substitute a different candidate or tip.                                                                                                                                                            |
| `Review branch does not include its recorded import baseline` | Integration was aborted/incomplete, history was rewritten, or metadata/refs disagree. Finish and commit the baseline integration on the review branch before final merge.                                                                                                                            |
| `Review branch changed during the merge`                      | Preserve the changed review separately and investigate the originally recorded source tip and target state. Retrying does not silently select the newer tip.                                                                                                                                         |
| Target merge conflicts                                        | Stay on the recorded target, resolve paths, stage them, commit the merge, and rerun the same explicit merge command. It recognizes the included review tip and proceeds to cleanup without another merge commit. `git merge --abort` leaves the recorded target binding and service branches intact. |
| `recorded merge is no longer included in this target`         | Inspect resets/rebases and the recorded target/source commits. Restore verified merge ancestry before retrying cleanup; the helper will not delete branches on this target history.                                                                                                                  |

The helper neither requires `ready` nor runs registry/type/build/test validation. A manually recovered failed review can merge once its ancestry checks pass, so finish and validate its metadata before using the helper.

## 7. Cleanup conditions and partial success

Cleanup iterates only the selected record's candidate and review roles. It never scans branch name prefixes to delete all service branches. For each branch:

1. If its local ref is absent, record `missing` and continue.
2. Otherwise require the current tip to equal the recorded candidate commit, or the review `merge.sourceCommit` selected for the successful target merge. A branch advanced even to an already-merged tip is retained if the recorded tip differs.
3. Require that it is not checked out in any registered worktree.
4. Require the tip to be an ancestor of current target `HEAD`.
5. Delete using normal `git branch -d`, recording command errors as retained reasons. Git permissions/locks and Git's own deletion checks can still prevent cleanup.

Retained reasons include `Branch changed since it was recorded`, `Branch is checked out in a worktree`, `Branch commits are not included in the merge target`, and the underlying Git deletion error. Baseline and unrelated branch refs are outside the cleanup set. No remote ref is touched.

`Merge succeeded; some branches were retained` means the target merge already succeeded. The command exits nonzero with status `merged` and phase `cleanup`; do not repeat the import to address this. Inspect `cleanup` and events, preserve any extra branch work, release the relevant worktree/lock, and retry the same review command from the recorded target. If a branch was deliberately removed after inspection, retry records it as `missing`. If all branches are absent/deleted, status becomes `complete` and phase `done`.

A process killed after the Git merge but before saving its commit can resume by detecting that the review tip is already included. A kill between deletion and its ledger update is also recoverable because an absent local branch is accepted. The ancestry/tip checks still apply; retry is not a bypass for changed or discarded history.

## 8. Registry, aliases, and validation failures

The internal post-integration command is `node scripts/vendor/import.ts registry`. It regenerates framework catalogs/artifacts and updates `registry.json`, then the update workflow commits that root metadata if changed. Full `pnpm registry:build` first invokes `shadcn build` for native entries, then runs the same framework builder. Neither registry path starts an import ledger operation by itself.

| Failure                                                              | Check and recovery                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Spark aliases are stale` / `Missing or invalid Spark alias`         | Root `@spark/<name>/*` paths must exactly match all `packages/<name>/src` roots, including internal dependencies. Run `pnpm aliases:sync`, inspect changes, and format `tsconfig.json` if the standalone sync rewrites it. Import generation does both sync and formatting; verification and registry generation only check aliases. |
| `Invalid Spark alias` / `Source outside component src`               | Inspect the alias shape and target. Cross-component aliases cannot escape their component root with `..`; local same-component source imports remain relative.                                                                                                                                                                       |
| `Unresolved installed source`                                        | A registry-bound source imports a local target outside the known locked/starter/native file set. Register intended helper files in import/registry tooling rather than adding an untracked implementation file only.                                                                                                                 |
| `REGISTRY_BASE_URL must be an absolute HTTP(S) URL`                  | Supply a valid HTTP(S) base and regenerate. The URL participates in release identity and immutable registry dependencies.                                                                                                                                                                                                            |
| `Unvendored import`                                                  | Verification found a remaining `@ark-ui/`, `@zag-js/`, `$lib/`, or `@spark-ui/` import. Correct the graph registration/rewrite or local edit.                                                                                                                                                                                        |
| `Unresolved import`                                                  | Verification found a relative/`@spark/` target missing from the registered locked source/starter set. Restore the file or register/reconcile the intended local helper.                                                                                                                                                              |
| `Framework dependency in common source`                              | A common module references a React/Svelte source tree or framework runtime. Move framework-specific behavior into the adapter boundary or correct the import.                                                                                                                                                                        |
| Missing registry files, invalid JSON, shadcn errors, or write errors | Inspect the exact command/path and source/catalog state. The builder returns without work when no source manifest exists; successful command exit alone is not evidence of emitted vendored artifacts.                                                                                                                               |
| Type failures after a successful import                              | Generation traverses/rewrites modules; it does not prove TypeScript correctness, install npm dependencies, or update root dependency versions automatically. Inspect declared external requirements, framework tooling, compiler libraries, and actual source APIs. Date Picker needs `ES2023.Array` for `findLastIndex`.            |

`verify-imports` validates registered import boundaries and common/framework separation. It permits intentional implementation edits; it does not check generated hashes like bootstrap, perform a full type check, or prove consumer runtime behavior.

Run the applicable checks on the recovered review branch before final merge:

```sh
pnpm test:importer
pnpm verify-imports
pnpm check
pnpm registry:build
pnpm build
pnpm storybook:build
```

For changes affecting distributed installation or runtime behavior, also use `pnpm test:registry`, then `pnpm test:browser`; the browser suite depends on consumer fixtures from the registry suite. `PLAYWRIGHT_CHROMIUM_EXECUTABLE` can select a compatible installed Chromium. Consumer fixtures are under ignored `.vendor-tests/`.

Use the package manager pinned in `package.json` and installed dependencies (`pnpm install`). Node must support built-in TypeScript stripping (>=22.18; this environment uses Node 26). Missing `typescript-parser`, Prettier, Svelte tooling, pnpm, Git, or shadcn commands are toolchain/install failures, not component-selection errors. `pnpm check` includes importer types, imported React/Svelte types, aliases, and formatting; `ready` and `complete` ledger statuses do not attest that it passed.
